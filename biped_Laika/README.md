# biped_Laika

A 12-DoF biped controlled by a reinforcement-learning policy exported to ONNX. This guide takes a policy
trained on the model in this folder to the real robot:

**match the parameters → match the interface → validate in simulation → hoist → ground.** Do not skip steps.

The authoritative configuration is [`biped_Laika.yaml`](biped_Laika.yaml). Every number below comes from it;
if this page and the file ever disagree, the file is right.

**Supplied with each robot, not part of this repository** — have these before you power the robot:
the robot computer's address and login; the power-up sequence and the location of the 48 V emergency stop;
where and how to attach the hoist; and the configuration file calibrated for your unit (see section 5.1).

## 1. Model

| File | Use |
|---|---|
| `biped_Laika.urdf` | URDF |
| `biped_Laika.xml` | MuJoCo model (contact between nested neighbouring meshes already excluded) |
| `usd/laika_v3.usd` | Isaac Lab asset (self-collision filter pairs already applied) |
| `isaac_values.py` | The configuration as plain Python dictionaries for the Isaac side: joint order, limits, actuator parameters, observation spec, profiles. Generated by `tools/export_isaac.py` |
| `meshes/` | STL meshes, simplified for display and collision. Mass, centre of mass and inertia come from the URDF / MJCF, not from the meshes |

Total mass **11.961 kg**; `base_link` **4.119 kg**. If you trained on a copy of the model obtained earlier,
compare these two numbers first — a policy trained with different masses needs fine-tuning on this model
before it will stand on the robot.

**Actuator values inside the model files are placeholders.** The effort and velocity limits, joint damping
and friction in the URDF, the drive gains and limits stored in the USD, and the force range in the MuJoCo
file come from the CAD export and the converters. Always override them with the values of the config
(`isaac_values.ACTUATORS`, section 2).

If you convert the URDF to USD yourself: the calf and ankle-roll link meshes overlap at the zero pose. Add
collision filter pairs (`CONTACT_EXCLUDE_PAIRS` in `isaac_values.py`) before enabling self-collision,
otherwise the robot is pushed around by phantom contact forces while standing still. The supplied USD already
has them.

## 2. Parameters your training must match

**Joint order** — observations and actions use this order everywhere, left leg then right leg:

```
l_hip_pitch, l_hip_roll, l_hip_yaw, l_knee, l_ankle_pitch, l_ankle_roll,
r_hip_pitch, r_hip_roll, r_hip_yaw, r_knee, r_ankle_pitch, r_ankle_roll      (each with the suffix _joint)
```

Isaac Lab's default joint order interleaves left and right. Select joints explicitly in this order for both
observation and action terms (`preserve_order=True`). This is the most common mistake in externally trained
policies.

**Actuators.** Position PD runs inside the motor: `tau = clip(kp·(q_des − q) − kd·qd, ±torque limit)`.

| Motor | Joints | kp | kd | Torque limit N·m | Speed limit rad/s | Armature | Coulomb friction N·m |
|---|---|---|---|---|---|---|---|
| RS06 | hip_pitch, knee | 30 | 1.5 | 18 | 10 | 0.0070 | 0.15 |
| RS02 | hip_roll, ankle_pitch | 20 | 1.0 | 17 | 20 | 0.0032 | 0.12 |
| RS00 | hip_yaw, ankle_roll | 12 | 0.6 | 11 | 33 | 0.0015 | 0.13 |

Viscous damping is 0.02 N·m·s/rad for all three.

- **Torque and speed limits are stored in the motor firmware.** Simulation must not exceed them. Watch the
  10 rad/s limit of the RS06 in particular: fast motions learned without it cannot be reproduced on the robot.
- **Different gains are a different robot.** A policy only works with the gains it was trained with. The
  robot runs the set above (`rl_default`).
- Control rate **50 Hz**. An action takes **1–2 control steps** to reach the motors.

**Target rate limiter.** On the robot every joint target passes through a rate limiter before it reaches the
motor (`slew.py`): per control step the commanded position moves by at most `speed limit × 0.02 s` towards the
policy's target — 0.2 rad for hip pitch and knee, 0.4 rad for hip roll and ankle pitch, 0.66 rad for hip yaw
and ankle roll. (Right after enabling, until a joint has first reached its target, the limit is 1 rad/s.)
`tools/sim2sim.py` models this stage. The reference policies were trained without an explicit model of it,
relying on the simulator's joint speed limit instead, and then validated with it in MuJoCo; if your policy
commands large target jumps on the knees, either model the limiter in training or check the effect in
section 4.

**Reference simulation setup.** The reference policies were trained in Isaac Lab 2.3 on Isaac Sim 5.1 with
rsl_rl 3.1, with these settings. None of them is mandatory, but each is a place where a mismatch shows up on
the robot:

| Setting | Value |
|---|---|
| Physics step, decimation | 0.005 s × 4 (= 50 Hz control), 20 s episodes |
| Actuator model | One `ImplicitActuatorCfg` per motor model: `stiffness` = kp, `damping` = kd, `effort_limit_sim` = torque limit, `velocity_limit_sim` = speed limit, `armature`, `friction` = `dynamic_friction` = Coulomb friction, `viscous_friction` = viscous damping |
| Friction units | Torques in N·m. This holds from Isaac Sim 5; earlier versions take a dimensionless coefficient |
| Articulation | Self-collision enabled (with the USD's filter pairs), 8 position / 0 velocity solver iterations, soft joint-limit factor 0.9 |
| Observation noise (uniform, before scaling) | Angular velocity ±0.2 rad/s, gravity ±0.05, joint angle ±0.01 rad, joint velocity ±1.5 rad/s |
| Action delay | 0–0.06 s, drawn once per environment at reset, applied as a fractional-step lag of the joint targets |
| Randomisation (`domain_rand` in the config) | kp ×0.8–1.2, kd ×0.7–1.3, joint friction −0.05…+0.10 N·m, torso centre of mass ±20 mm |
| Terminations | Contact on the base link, tilt above 0.7 rad, base lower than 0.25 m, time-out |

Reward design and command curriculum are yours. The speeds the reference walking policy is used at on the
robot are 0.20 m/s forward, 0.10 m/s sideways and 0.30 rad/s turning; train your command ranges to cover what
you intend to drive, with margin.

`isaac_values.py`: the top-level `DEFAULT_JOINT_POS`, `ACTION_SCALE` and `INIT_BASE_HEIGHT` belong to the
default (standing) contract. For a walking task take the nominal pose, action scale and base height from
`POLICY_PROFILES["walk"]` (or your own profile).

Joint limits are in `joints[].range`. Note the knees: left [−2.094, 0], right [0, 2.094] — the zero pose
(leg straight) sits exactly on the limit.

## 3. Policy interface

**What the robot can give a policy:** IMU angular velocity, gravity direction, joint angles, joint velocities,
the previous action, the velocity command, and optionally a gait clock. There is no base linear velocity, no
foot contact and no height. A policy whose actor observes any of those cannot run on the robot (they may
still go to the critic).

Base observation, 45 values, fixed order and scaling:

| Term | Size | Scale | Meaning |
|---|---|---|---|
| `base_ang_vel` | 3 | 0.25 | Angular velocity in the body frame, rad/s |
| `projected_gravity` | 3 | 1.0 | Unit gravity vector in the body frame; [0, 0, −1] when upright |
| `commands` | 3 | [2.0, 2.0, 0.25] | vx, vy (m/s), wz (rad/s) |
| `joint_pos_rel` | 12 | 1.0 | Joint angle − nominal pose, rad |
| `joint_vel` | 12 | 0.05 | Joint velocity, rad/s |
| `last_action` | 12 | 1.0 | Previous network output, after clipping to ±1 and before scaling; zeros on the first step |

Body frame: x forward, y left, z up. Joint angles are in URDF coordinates; the motor direction and zero
offset are handled by the `sign` / `offset` entries of the config.

Action: `joint target = nominal pose + action_scale × clip(network output, ±1)`, clamped to the joint limits,
then passed through the target rate limiter of section 2.

**Profiles** (`policy_profiles` in the config). Use an existing one if you can:

| Profile | Observation | Nominal pose | Action scale | Gait clock | Notes |
|---|---|---|---|---|---|
| *(default)* | 45 | Legs straight (all zeros) | 0.25 | none | Used by the standing policy |
| `walk` | 47 = 45 + gait phase (2) | Shallow crouch: hip ∓0.15, knee ∓0.3, ankle ∓0.15 | 0.5 | 0.40 s | The simplest walking interface — **recommended for your own policy** |
| `omni` | 215 = 47 + history (168) | as `walk` | 0.5 | 0.50 s | Adds four frames of history |
| `omni_ff` | 215 | as `walk` | 0.5 | 0.50 s | `omni` plus a lateral feed-forward term; used by the reference walking policy |

- Gait phase = `[cos 2πφ, sin 2πφ]`, where φ is the fractional part of (time ÷ period), with time counted
  from the moment the policy is enabled or, in the stand + walk state machine, from the entry into walking.
  It is an open-loop clock, independent of the robot's state.
- History = the previous four control steps of [angular velocity, gravity, joint angles, joint velocities,
  last action] (42 values each, newest first, current step excluded, scaled as in the table). The exact
  definition is `build_obs` in `tools/policy_io.py`. Isaac Lab's built-in observation history has a different
  layout; write this block yourself.
- The nominal pose has opposite signs on the two legs (left hip −0.15, right hip +0.15) because the joint
  axes are mirrored.

### If your interface differs

The order and scaling of the 45 base values are fixed in code. What you can choose is the nominal pose, the
action scale, the clock period, and whether a gait phase / history block is appended at the tail.

- **Different nominal pose, scale or period:** add a profile to `policy_profiles` in the config:

  ```yaml
  policy_profiles:
    my_walk:
      action_scale: 0.3
      init_base_height: 0.3804          # see below
      cycle_time_s: 0.6                 # omit together with obs_extra if you use no clock
      obs_extra:
        - {name: gait_phase, dim: 2, scale: 1.0}
      nominal_pose:
        l_hip_pitch_joint: -0.20
        # ... all 12 joints
  ```

  Then run `python tools/export_isaac.py && python tools/contract_check.py --onehot` (expect `ALL PASS`).

  `init_base_height` is the height of the base above the ground when the robot stands in the nominal pose
  with its soles on the floor. It is exported to `isaac_values.py` as the spawn height for training; the SDK
  tools do not compute it. Keep the nominal pose such that the soles stay flat (hip − knee + ankle pitch = 0
  with the signs of the left leg), and recompute the height for a different crouch — a few millimetres of
  error only cause a small drop at reset.

  **The same profile must be in the config on the robot computer**, or the stamped policy is refused there.
  That file also carries the unit's calibration, so add the profile to it by hand rather than overwriting it.

- **Different observation content, order or scaling** (for example base linear velocity, or a different
  history layout): retrain or fine-tune to the interface above. Simulation and deployment share one
  observation implementation; adapting on the deployment side breaks that guarantee.

### Exporting to ONNX

One input of shape `[1, obs_dim]`; the first 12 values of the first output are the action.
**Observation normalisation must be inside the ONNX**: the deployment code feeds the vector scaled as in the
table straight into the network. With rsl_rl, export through Isaac Lab's `export_policy_as_onnx(...,
normalizer=...)` so that the normaliser is included.

`tools/export_ckpt.py` is a shortcut for one case only: an rsl_rl actor that is a plain MLP with ELU
activations and **no** observation normalisation. It refuses a checkpoint that contains a normaliser.

## 4. Stamp, then validate in simulation

**Stamping** writes the policy's profile and the robot parameters it was built for into the ONNX metadata.
Simulation and deployment verify the stamp when loading and refuse to run on an interface mismatch, instead
of letting the robot move with misaligned inputs. Unstamped files are refused by default. Stamping does not
check the network's input size; the simulator does when it loads the file.

```bash
python tools/onnx_manifest.py --stamp my_policy.onnx --profile walk      # metadata only; weights are untouched
python tools/onnx_manifest.py --show  my_policy.onnx
```

**MuJoCo validation.** `--delay 2` applies a two-step action delay (the default is 0); `--jitter 0.05`
perturbs the initial joint angles.

```bash
python tools/sim2sim.py --policy my_policy.onnx --cmd 0 0 0   --delay 2 --jitter 0.05      # in place
python tools/sim2sim.py --policy my_policy.onnx --cmd 0.2 0 0 --delay 2 --jitter 0.05      # forward
python tools/sim2sim.py --policy my_policy.onnx --cmd 0 0 0.3 --delay 2 --jitter 0.05      # turn
mjpython tools/sim2sim.py ... --view          # with a window (plain python on Linux)
```

Then sweep what differs on a real robot:

```bash
... --delay 0      /  --delay 3
... --kp-scale 0.8 /  --kp-scale 1.2      --kd-scale 0.7  /  --kd-scale 1.3
... --friction 0.5
... --push 4 3.0                          # a 4 N·s sideways impulse at t = 3 s
... --foot-box                            # flat box soles instead of the foot meshes' convex hulls
... --seed 1  /  2  /  3
```

Foot contact: by default the feet collide with the convex hull of their mesh, which touches the ground at a
few points; `--foot-box` replaces it with a flat box sole. Neither is the real sole — a policy should pass
with both.

**Reading the report.** The first line says whether the robot survived; the exit code follows it. Survival
alone is a weak test (a policy that outputs zeros survives most runs), so look at:

- **actual speed against the command** — is it tracking;
- **tilt** — steady-state mean of a few degrees;
- **torque peak relative to the limit** — a joint that stays near 100 % has no margin and will run hot;
- **touchdown force** — in multiples of body weight; much more than the reference is loud and hard on the
  gearboxes;
- **net yaw and lateral drift** on a straight command.

**Reference numbers.** The reference policies under the same commands (`--delay 2 --jitter 0.05`, 10 s,
seeds 0–2; the walking policy with `--power-scale 0.8`). Use them as a baseline, not as a target:

| Run | Survived | Actual speed | Max tilt | Torque peak / limit | Touchdown peak |
|---|---|---|---|---|---|
| Stand, command 0 | 3/3 | 0 | 1.5° | 31 % | — |
| Stand, `--push 8 3.0` | 3/3 | 0 | 5.5° | 41 % | — |
| Walk forward 0.2 m/s | 3/3 | vx 0.16–0.18, vy drift 0.03–0.04 | 13.8° | 77 % | 2.9 × body weight |
| Walk backward 0.2 m/s | 3/3 | vx −0.18…−0.19 | 8.9° | 75 % | 2.9 × |
| Side-step 0.1 m/s | 3/3 | vy 0.18–0.19 | 10.9° | 76 % | 3.2 × |
| Turn 0.3 rad/s | 3/3 | wz 0.11–0.21 | 9.5° | 73 % | 2.4 × |
| Forward, `--foot-box` | 3/3 | vx 0.19–0.20 | 10.2° | 68 % | 2.3 × |
| Forward, `--friction 0.5` | 3/3 | vx 0.12–0.16 | 18.7° | 81 % | 2.9 × |
| Forward, `--push 4 3.0` | 3/3 | — | 13.8° | 79 % | — |
| Forward, `--push 6 3.0` | 1/3 | — | — | — | — |
| Forward, `--push 8 3.0` | 0/3 | — | — | — | — |

The reference walking policy tracks forward and backward speed well, overshoots the side-step command,
under-tracks turning, drifts in yaw on a straight command, and does not withstand strong sideways pushes
while walking. Its outputs also saturate at the action clip on the hip-roll joints for most of the gait.

**Together with the standing policy.** This is how the robot normally runs: it stands, switches to walking
when a velocity command arrives, and switches back one second after the command ends.

```bash
python tools/sim_fsm.py --policy my_policy.onnx --stand-policy biped_Laika/policies/stand.onnx \
    --script "2:w3,8:w2" --duration 13 --delay 2 --jitter 0.05
# --script: at 2 s walk forward (0.2 m/s) for 3 s, at 8 s for 2 s
```

The hand-over between standing and walking is not exercised when a policy runs alone, and it is one of the
likeliest places to fall on the robot. Do not skip this run. The script drives forward walking only.

**Margin against oscillation.**

```bash
python tools/policy_gain_probe.py --policy my_policy.onnx --stand-policy biped_Laika/policies/stand.onnx \
    --delay 1 --jitter 0.05 --script 3:w6 --duration 12 --quiet
```

MuJoCo has neither the velocity noise nor the structural compliance of the real robot, so a policy that is
quiet in simulation can still buzz at 25 Hz on hardware. This tool measures the policy's own feedback gains.
As a guide, the reference walking policy measures a `last_action` self-loop eigenvalue of about −0.65 and a
sign-flip rate of about 20 %. Values near −0.9 and 60 % have produced audible buzzing on hardware; add an
action-smoothness penalty and retrain before going further.

**What the hoisted robot should look like.** `python tools/sim2sim.py --policy my_policy.onnx --suspend-pivot`
simulates the robot hanging from a single point (`--suspend` holds the base rigidly). Compare the leg motion
with what you see in section 5.2.

## 5. On the robot

Connect as described in [`docs/connect.md`](../docs/connect.md) (method A: log in to the robot computer).
Read [`docs/safety.md`](../docs/safety.md) first. Run the commands below on the robot computer from the
repository root.

### 5.1 Checks before the first enable (motors disabled)

```bash
python tools/mc02_selftest.py                  # board answers, boot flags clear, ids 1–6 on CAN1 and 7–12 on CAN2
python tools/set_torque.py --check             # the 12 motors read back 18 / 17 / 11 N·m
python tools/set_can_timeout.py --check        # the 12 motors read back 10000 (= 0.5 s)
python tools/imu_reader.py --verify-axes       # nod the torso down, tilt it right: both checks pass
```

**Calibration check.** `joints[].sign`, `joints[].offset` and `imu.mount_rpy_deg` in the config belong to one
physical robot. The file in this repository holds the values of one particular unit: on your robot, use the
configuration delivered with it, and confirm that it matches before any motor is enabled — a wrong offset
makes the robot move to a wrong pose at full gain.

```bash
# robot computer: the bridge in watch mode never enables the motors
python bridge.py
# your computer: the model mirrors the real joint angles (mjpython on macOS)
python mirror_viewer.py --model biped_Laika/biped_Laika.xml --host <robot-ip> --mode watch
```

With the robot hanging or lying with its legs straight, the model must show straight legs; move each joint
by hand and check that the same joint moves in the same direction in the viewer. If a joint is offset or
moves the wrong way, do not enable: calibrate first (section 7). Stop the bridge before continuing.

### 5.2 On the hoist (feet off the ground, line taut)

When a command starts, there is no confirmation prompt: about three seconds after launch (IMU settling,
parameter read-back) the 12 motors are enabled at the policy gains, hold the pose they are in, and then move
to the policy's targets at no more than 1 rad/s. Keep clear of the legs from the moment you press Enter.

```bash
# 1. PD only, no network: the robot moves slowly to your profile's nominal pose and holds it
python tools/deploy_policy.py --policy zero --no-imu --policy-profile walk --duration 5

# 2. Each joint is moved by about 3 degrees in turn: right joint, right direction, right amplitude. All 12 must PASS
python tools/deploy_policy.py --policy zero --no-imu --onehot-real --policy-profile walk

# 3. The reference standing policy: confirms this robot and this connection are healthy
python tools/deploy_policy.py --policy biped_Laika/policies/stand.onnx --duration 10

# 4. Your policy with a zero command; first at 10 % amplitude, then at full amplitude
python tools/deploy_policy.py --policy my_policy.onnx --power-scale 0.1 --duration 10
python tools/deploy_policy.py --policy my_policy.onnx --duration 10 --log real_logs/my_hang.csv

# 5. Your policy inside stand + walk, driven by a script: W is "pressed" at 2 s and at 9 s
python tools/deploy_policy.py --policy my_policy.onnx --stand-policy biped_Laika/policies/stand.onnx \
    --fsm-script "2:w,9:w" --teleop-hold 4 --duration 16 --log real_logs/my_fsm_hang.csv
```

In step 5 each scripted press holds the forward command for `--teleop-hold` seconds; the first 0.8 s of that
is the transition from the standing pose to the walking pose, so 4 s gives about 3 s of walking command. The script
syntax here is `time:key` only (keys `w a s d q e`, `1` = stand, `2` = walk); a duration suffix as in
`sim_fsm.py` is not accepted. The terminal should show the state machine going STAND → LOCO → STAND twice.

`--power-scale K` multiplies your policy's output: at 0.1 the robot stays near the nominal pose and shows the
pattern of the motion at a tenth of the amplitude. It is a tool for the first look on the hoist. For walking,
use the value you validated in simulation (normally 1.0, i.e. no option).

Legs swinging in the air is normal on the hoist. Watch for buzzing or high-frequency shaking, for motion that
does not resemble the `--suspend-pivot` simulation, and for repeated watchdog messages in the terminal.

If step 2 reports FAIL for a joint: wrong amplitude or a neighbouring joint moving points to the calibration
offsets (section 7); a joint moving in the opposite direction means its `sign` in the config is wrong — fix
the sign by hand, then recalibrate.

To see exactly what the network receives on the robot, add `--dump-frames 50 --dump-path dump.npz` to
step 4, copy `dump.npz` to your computer and run
`python tools/contract_check.py --replay dump.npz --policy my_policy.onnx`: the same observations must give
the same outputs on both machines (within 1e-6). The `obs` array in the file is the vector fed to the network
on the robot — compare it term by term with the observation in your training environment.

### 5.3 On the ground

Two people: one at the keyboard, one holding the hoist line.

1. Stand the robot on level ground with the hoist line attached and just slack: legs straight, feet flat and
   parallel, roughly 21 cm apart. The second person steadies the torso upright.
2. Start the command below. About three seconds later the motors enable and the standing policy takes over;
   the terminal prints that the 12 joints are enabled. The helper can let go of the torso once the robot
   holds itself, and keeps the line slack but in hand.
3. **Hold** W / S to walk forward / back, A / D to side-step, Q / E to turn. One press gives a command for
   one second; holding the key keeps it going. One second after you let go the robot returns to standing.
   Space zeroes the command at once.
4. To finish: let the robot return to standing, **take up the slack in the hoist line**, then press `x`.
   Every way of ending the program — `x`, the PS button, the end of `--duration`, Ctrl+C — puts the motors in
   damping and then disables them: the robot goes limp and must be held by the line or by hand. There is no
   sit-down motion.

```bash
python tools/deploy_policy.py --policy my_policy.onnx --stand-policy biped_Laika/policies/stand.onnx \
    --teleop --teleop-speed 0.10 --teleop-side 0.05 --teleop-turn 0.20 --log real_logs/my_ground.csv
```

Raise `--teleop-speed` gradually. For a gamepad replace `--teleop` by `--pad` (a PlayStation controller
paired with the robot computer): left stick walks, right stick turns, **hold R1 to move**, Options = stand,
Share = stop, PS = quit.

The reference walking policy on the ground, for comparison:

```bash
python tools/deploy_policy.py --policy biped_Laika/policies/walk.onnx --power-scale 0.8 \
    --stand-policy biped_Laika/policies/stand.onnx \
    --teleop --teleop-speed 0.20 --teleop-side 0.1 --teleop-turn 0.30
```

`--power-scale 0.8` is part of how that reference policy is run (in simulation and on the robot).

### 5.4 Built-in protection

| Trigger | Action |
|---|---|
| Ctrl+C, or an exception in the policy | All motors to damping, then disabled |
| Torso tilt > 45° (`--max-tilt-deg`) | Same |
| No new IMU data for 0.1 s | Same |
| Torque limit or communication timeout stored in a motor differs from the config | Refuses to start |
| ONNX not stamped, or stamp does not match the config | Refuses to start |
| Host stalls for more than 100 ms | The MC02 board sends damping frames by itself; when the host returns the robot re-homes slowly |
| USB disconnected | Each motor releases after 0.5 s without commands |

## 6. Reference policies

Both are stamped; no profile needs to be given on the command line.

| File | Profile | Description |
|---|---|---|
| `policies/stand.onnx` | *(default, 45)* | Standing. Withstands an 8 N·s sideways push in simulation |
| `policies/walk.onnx` | `omni_ff` (215) | Omnidirectional walking: forward / back, side-step, turn. **Always run with `--power-scale 0.8`** |

Use them to verify a robot, a connection or an installation before trying your own policy. Their numbers in
simulation are in section 4.

- Speeds used on the robot: 0.20 m/s forward, 0.10 m/s sideways, 0.30 rad/s turning. Larger commands are
  outside what has been validated.
- The walking policy drifts slowly to the left when walking straight (a bias of the policy, also visible in
  simulation). With `--stand-policy`, add `--heading-hold --trim-vy -0.03` to compensate (yaw is held from
  the IMU and a small rightward velocity is added while walking); tune the trim in steps of 0.01.

## 7. Calibration

Recalibrate after replacing a motor or re-assembling a joint, when the check in section 5.1 does not match,
and whenever `--onehot-real` fails.

```bash
python tools/calib_stance.py --repeat 3            # robot posed in the zero stance, motors disabled; prints the result
python tools/calib_stance.py --repeat 3 --write    # writes it to the config once the numbers look right
```

Zero stance: legs straight, both soles flat on level ground, sole centres 214.5 mm apart, toes pointing
straight ahead and parallel, torso vertical. It takes two people — one holds the robot in the pose while the
other starts the sampling. The full posing requirements are at the top of `tools/calib_stance.py`. With
`--repeat 3` the tool reports the spread between the three poses: repeat until the spread is around one
degree or less. An error of one or two degrees is enough to make the robot veer, so take your time.

The tool measures offsets (and the IMU level). It does not determine a joint's direction: `sign` is set by
hand in the config and checked with the viewer (section 5.1) and `--onehot-real`.

## 8. Troubleshooting

| Symptom | Likely cause |
|---|---|
| Wild motion from the first step in simulation | Joint order (Isaac's interleaved default); nominal-pose signs left / right; observation scaling; normalisation missing from the ONNX |
| Stands in simulation but cannot walk | Gains, torque limits or speed limits in training differ from section 2 |
| Passes MuJoCo, buzzes on the robot | Strong feedback through joint velocity (run `policy_gain_probe`); trained without action-delay randomisation |
| Lags behind and sways more with every step on the robot | Trained without action delay (the robot has 1–2 steps) |
| Loud footfalls on the robot | No touchdown-impact penalty in training; step frequency too high |
| Falls at the moment of switching from standing to walking | Hand-over never tested with `sim_fsm`; the policy never saw a start from a static stand |
| `--onehot-real` fails on a joint | That joint's `offset` or `sign` is wrong (section 5.2) |
