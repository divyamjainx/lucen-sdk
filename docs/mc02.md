# The MC02 interface board

The MC02 is the board between the robot computer and the motors. This page covers what it does, how to wire
and check it, how it protects the robot, and how to re-flash it. To write your own host software for the
board, see [`mc02_protocol.md`](mc02_protocol.md).

## 1. What it is

- **One USB cable** to the robot computer. The board appears as a single USB serial device (CDC-ACM) with the
  product name `Lucen MC02 v1`. That one link carries both CAN buses and the IMU stream.
- **Two CAN buses.** CAN1 is `mc02:0` and CAN2 is `mc02:1` in the robot configs. Classic CAN at 1 Mbps,
  29-bit extended frames, no filtering. Frames pass through transparently in both directions: the firmware
  does not interpret the motor protocol. Everything motor-specific is on the host, in `robstride_mit.py`.
- **On-board IMU** (BMI088). Raw accelerometer and gyroscope samples are streamed at 500 Hz on the same USB
  link, time-stamped by the same clock as the received CAN frames. biped_Laika uses it; the
  attitude estimate is computed on the host (`tools/imu_reader.py`).
- **Link watchdog.** If the host goes silent, the board itself sends a pre-registered failsafe frame to every
  motor (section 7).

All robots use the same firmware. Boards are delivered flashed.

## 2. Which bus carries what

| Robot | Config | CAN1 = `mc02:0` | CAN2 = `mc02:1` |
|---|---|---|---|
| biped_Laika | `biped_Laika/biped_Laika.yaml` | left leg, ids 1-6 | right leg, ids 7-12 |
| humanoid_arm | `humanoid_arm/humanoid_arm.yaml` | left arm, ids 1-8 | right arm, ids 9-16 |
| Arm, leader-follower pair | `Arm/Arm_pair.yaml` | follower, ids 1-7 | leader, ids 8-14 |
| Arm, single | `Arm/Arm.yaml` | the arm, ids 1-7 | not used |

The assignment is the `bus:` column of the joint table in the robot's YAML, and the wiring must match it.
The self-test (section 6) checks it. If the two harnesses are exchanged, swap the connectors; do not edit the
config. wheeled_base is simulation-only in this release and its config has no bus assignment.

## 3. Power and wiring

1. **The board is powered from USB only**, by the robot computer. The CAN transceivers work on USB power. Do
   not feed the board from the 48 V motor supply: its power input accepts 12-24 V only.
2. **Motor power does not pass through the board.** The 48 V supply goes from the power distribution board
   straight to the motors. The power pins of the board's XT30 connectors are switched *outputs*; never connect
   motor power to them. They are not protected against 48 V fed back into them, and neither the connector nor
   the board traces can carry the peak current of a chain of motors. Leave the XT30 connectors unused.
3. **Connect only CAN L and CAN H, to the 2-pin ports.** CAN1 is the group of ports at the top right of the
   board, CAN2 the group at the top left. Each group has two 2-pin ports wired in parallel: they are the same
   bus, so one can be the way in and the other the way out of a daisy chain.
4. **Run one ground wire from the board to the motor power ground.** With USB power the board's ground is the
   robot computer's ground; without this wire the CAN signals have no common reference. It is required.
5. **Terminate each bus with 120 Ω at both ends**: one at the board (it has a position per bus, marked
   `CAN1 120R` and `CAN2 120R`) and one at the last motor of the chain. Do not assume; measure. With all power
   off, the resistance between CAN H and CAN L of each bus must be about 60 Ω.
6. **Do not trust the L / H markings.** The L / H marking on the board's 2-pin ports does not match the L / H
   marking on the motor harness: connected mark to mark, every motor on the bus stays silent (LEC = 3 in the
   self-test). Go by the self-test scan, not by the markings. If a whole bus is silent with LEC = 3 while the
   motors are powered, exchange L and H on that bus.
7. **Leave CAN3 unconnected** (the small connector on the left edge of the board). This firmware does not use
   it.

## 4. Status LED

| LED | Meaning |
|---|---|
| Green, blinking at 1 Hz | Firmware running, watchdog not configured (no program is driving the motors) |
| Blue, blinking at 1 Hz | Watchdog armed (a bridge or deployment is driving the motors) |
| Orange, blinking fast | Watchdog fired: the board is sending the failsafe frames |
| Red, steady | `boot_flags` is not 0 (CAN clock check failed, or the IMU did not initialise). Fix this before connecting motors (section 9) |
| Off, and no serial device | Firmware not running, or no USB power |

## 5. Device name

**Linux.** `bash setup.sh` installs a udev rule that matches the USB product name `Lucen MC02 v1` and creates
the fixed name `/dev/mc02`. Check it:

```bash
ls -l /dev/mc02                                    # a link to a ttyACM device
udevadm info -a /dev/ttyACM0 | grep product        # should show "Lucen MC02 v1"
```

Never write `/dev/ttyACM*` into a config: those numbers change with the order in which USB devices are
detected. The board's USB vendor / product id is the generic `0483:5740`, which is why the rule matches the
product name.

**macOS.** There is no udev. The board is `/dev/cu.usbmodem*`; put that name in the config's `mc02.port`, or
pass it with `--port`.

**One process at a time.** The board is a single serial device and is opened exclusively. The program that
drives the robot (the bridge or the deployment program) owns both CAN buses and the IMU. While it runs,
nothing else can open the board; stop it before running the self-test or the motor-parameter tools. A second
process fails with an error that starts with `[mc02]`.

**Two boards on one computer.** Every MC02 claims the name `/dev/mc02`, so with two boards plugged in that
name points to an arbitrary one, and commands meant for one robot could reach the other. The SDK refuses to
open `/dev/mc02` in that case and lists the boards. Give each config its own board through its permanent
path, whose name contains the board's USB serial number (derived from the MCU's unique id, so it differs per
board):

```bash
ls -l /dev/serial/by-id/ | grep MC02
# usb-Lucen_Robotics_Lucen_MC02_v1_<serial>-if00
python tools/mc02_selftest.py --config <robot yaml> --port /dev/serial/by-id/<name>   # which motor ids are on this board?
```

```yaml
mc02:
  port: /dev/serial/by-id/usb-Lucen_Robotics_Lucen_MC02_v1_<serial>-if00
  watchdog_ms: 100
```

## 6. Self-test

`tools/mc02_selftest.py` talks to the board and scans both buses. By default it never enables a motor and
nothing moves. Stop the bridge or deployment program first, and run it from the repository root:

```bash
python tools/mc02_selftest.py                                            # biped_Laika (the default config)
python tools/mc02_selftest.py --config humanoid_arm/humanoid_arm.yaml
python tools/mc02_selftest.py --config Arm/Arm_pair.yaml
python tools/mc02_selftest.py --config Arm/Arm.yaml
python tools/mc02_selftest.py --config <robot yaml> --port <device>     # default port: mc02.port from the config
```

The config supplies the port, the motor ids expected on each bus, and the watchdog timeout.

| Step | What it does | What you want to see |
|---|---|---|
| `[1] PING` | Asks the board to identify itself; the answer is called PONG | A line `fw <major>.<minor>  proto v1  MCU UID <hex>`, and the BMI088 reported online with its range codes (acc=1, gyr=1). With no PONG the tool stops here with exit code 2 |
| `[2] STATUS` | Reads the board's status block | CAN clock check passed (`boot_flags` = 0). For each bus: `drop=0/0`, no `BUS-OFF`, no `err-passive`. USB error counters at 0, or at least not growing from run to run |
| `[3]` bus scan | Sends an identity request to ids 1-14 on both buses (further if the config uses higher ids). A powered motor answers without being enabled | Each bus answers with exactly the ids the config assigns to it. After the scan, LEC (the CAN controller's last error code) is 0 or 7 on both buses |
| `[4]` round-trip time | 100 PINGs; prints p50 / p95 / max | Informational. Expect a p95 of 2-4 ms at most |

`boot_flags` has two bits: bit 0 = the CAN clock does not match the bit timing, so the CAN bit rate is wrong;
bit 1 = the IMU failed to initialise. Either one makes the LED steady red.

The run ends with `SELFTEST PASS` (exit code 0) or `SELFTEST FAIL (n)` (exit code 1). It fails on: a
protocol version other than 1, IMU not online, CAN clock mismatch, or a bus whose answers differ from the
config. If one bus answers with the other bus's ids, the tool says that the two buses are swapped.

Work through these stages in order:

| Stage | Condition | Command | Expected |
|---|---|---|---|
| 1 | USB only, motor power off | `python tools/mc02_selftest.py --config <robot yaml>` | LED green at 1 Hz. `[1]` shows the PONG and the BMI088 online; `[2]` shows the CAN clock check passed. `[3]` finds no motors and LEC = 3 (nobody acknowledges), so the run ends with `SELFTEST FAIL`. That is normal at this stage |
| 2 | Motor power on, motors not enabled | same | `[3]` matches the config on both buses, LEC 0 or 7, `SELFTEST PASS` |
| 3 | same, robot at rest (robots that use the IMU) | add `--imu` | About 500 samples in 1 s; mean acceleration magnitude about 9.8 m/s^2; mean angular rate about 0 |
| 4 | biped_Laika hoisted, arms resting; motor power on | add `--wd-test` | FIRED 100-140 ms after the host goes silent, then RELEASED |

**`--imu`** streams IMU samples for 1 s at 500 Hz and prints the number of samples received and the mean
acceleration (m/s^2) and angular rate (rad/s) per axis. It fails if no sample arrives.

**`--wd-test`** checks that the board acts on its own when the host goes silent. The motors are not enabled
at any point. It:

1. registers one failsafe frame for each motor found by the scan (16 at most), repeated every 10 ms. The
   frame is a motor *stop* command, which does nothing to a motor that is not enabled;
2. arms the watchdog with `mc02.watchdog_ms` from the config, keeps the link busy for 0.5 s, then goes
   silent;
3. expects the board's FIRED event between `watchdog_ms` and `watchdog_ms` + 40 ms after the last packet
   (100-140 ms with the default). It fails at `watchdog_ms` + 80 ms or later, or if no event arrives within
   1 s;
4. sends one packet and expects the RELEASED event within 0.5 s;
5. disarms the watchdog and clears the failsafe frames.

If the scan found no motors, only the event path is tested.

## 7. Protection behaviour

| Event | What the board does | What the motors do |
|---|---|---|
| Host silent for more than `mc02.watchdog_ms` (100 ms), board still powered | Replays each motor's registered damping-only frame every 10 ms, until the host returns | Go to damping |
| Host returns | Stops replaying; the watchdog is armed again | The host re-homes them at the slow rate |
| USB unplugged | Nothing: **the board is powered from USB and is off** | Keep executing the last command for `can_timeout` (0.5 s), then disable themselves |

### Host silent: the link watchdog

When the bridge or the deployment program enables the motors, it

1. registers one failsafe frame per motor with the board: that motor's damping-only command (kp = 0,
   kd = 1.0, no position, velocity or torque target), to be repeated every 10 ms;
2. arms the watchdog with `mc02.watchdog_ms` from the robot's YAML (100 ms in the shipped configs).

From then on every valid packet from the host restarts the watchdog; the normal 50 Hz command stream is the
heartbeat. If no valid packet arrives for longer than the timeout, the board sends the registered frames by
itself, every 10 ms, until the host returns. This covers a program that crashed, was killed or stalled, a
hung USB stack on the robot computer, and a robot computer that restarts while its USB port stays powered.
The LED blinks orange fast.

When the host returns, its first valid packet ends the replay. A program that was only stalled notices that
the watchdog fired, logs it, drops its old targets, sends damping-only commands until it has joint feedback
newer than the event, and then re-homes: it moves the joints from where they are now to the commanded pose at
the slow homing rate. Without this the joints would snap back to targets the robot has moved away from.

After a crash or a kill there is no host to return. The motors stay in damping, with the LED blinking orange
fast, until the program is started again.

On a normal exit the host clears the failsafe frames and disarms the watchdog, then puts the motors in
damping and disables them itself.

100 ms is five control steps at 50 Hz. Do not set `mc02.watchdog_ms` close to the 20 ms control period:
ordinary scheduling jitter on the host would then trigger it.

To see it work, hoist biped_Laika (or let the arm rest), start the bridge or deployment program, and from a
second terminal:

```bash
kill -STOP <pid>     # frozen host: after 100 ms the joints go to damping, LED orange fast
kill -CONT <pid>     # the program logs that the watchdog fired and re-homes at the slow rate
kill -9 <pid>        # joints go to damping and stay there until the next start
```

### USB unplugged: the motors' own timeout

**Unplugging the USB cable powers the board off.** There is then no watchdog and no failsafe frame, and the
motors keep executing the last command they received. The only protection in this case is the CAN timeout
inside each motor: a motor that receives no CAN command for that long disables itself and the joint is
released.

The value is `can_timeout` in the robot's YAML, in units of 50 µs: `10000` = 0.5 s. A motor's factory setting
is 0, which means off, so it must be written to every motor before torque is applied:

```bash
python tools/set_can_timeout.py --config <robot yaml> --check           # read back from every motor and compare
python tools/set_can_timeout.py --config <robot yaml> --write --save    # write, and store in the motor
```

`--write` without `--save` changes the value only until the motor is powered off. Without `--config` the
tool uses biped_Laika. Stop the bridge or deployment program first. The biped deployment program
(`tools/deploy_policy.py`) reads the value back at start-up and refuses to run if a motor differs from the
config. The bridge does not make this check: for the arms, run `--check` yourself, and again after replacing
a motor.

While the board is alive this timeout never triggers: the motors keep receiving either the host's commands
or the board's failsafe frames, 10 ms apart. It only decides how long the joints hold their last target after
the link is completely lost. Do not make it much shorter: while the motors are being enabled one after
another, gaps of tens of milliseconds without commands are normal.

The link does not reconnect by itself. After the cable has been unplugged, the program reports the lost link
(a line starting with `[mc02]`) and stops driving the motors. Plug the cable back in and start the program
again.

## 8. Updating the firmware

Boards are delivered flashed and normally never need this. The firmware image is not part of this repository:
if a board has to be updated or recovered, Lucen supplies the image (`<firmware image>` below). Stop the bridge
or deployment program first.

```bash
sudo apt install dfu-util stlink-tools        # stlink on macOS: brew install stlink
```

### Normal path: USB DFU, no extra hardware

```bash
python tools/mc02_selftest.py --dfu           # the firmware restarts into the MCU's built-in USB bootloader
lsusb | grep -i 0483:df11                     # should show "STM Device in DFU Mode"
sudo dfu-util -a 0 -s 0x08000000:leave -D <firmware image>
```

`--dfu` uses the port from the config, or `--port`. If `0483:df11` does not appear, the board did not enter
the bootloader; use a recovery path.

### Recovery path 1: BOOT0 pad

Short the BOOT0 pad (P14) and reset the board. It starts in the same USB bootloader (`0483:df11`); flash it
with the `dfu-util` command above.

### Recovery path 2: ST-Link (SWD)

The SWD header is at the bottom left of the board: pin 1 = 3.3 V, pin 2 = GND, pin 3 = SWCLK, pin 4 = SWDIO.
Connect SWDIO, SWCLK and GND to the ST-Link and power the board from its own USB cable.

```bash
st-flash --reset write <firmware image> 0x08000000

# or with OpenOCD
openocd -f interface/stlink.cfg -f target/stm32h7x.cfg \
        -c "program <firmware image> 0x08000000 verify reset exit"
```

If the probe has no reset (NRST) line to the board, press the board's RESET button afterwards.

### Confirm that the board is running

1. The LED blinks green at 1 Hz.
2. `/dev/mc02` is back: `ls -l /dev/mc02`.
3. `python tools/mc02_selftest.py` gets a PONG, prints the firmware version, and reports the CAN clock check
   as passed and the BMI088 online.

## 9. Troubleshooting

| Symptom | Cause / what to do |
|---|---|
| LED off, no serial device | The firmware is not running, or there is no USB power. Check the cable and port; re-flash (section 8, recovery paths) |
| LED on, but no `/dev/mc02` | The udev rule is not active. `udevadm info -a /dev/ttyACM0 \| grep product` should show `Lucen MC02 v1`; run `bash setup.sh` and re-plug the board. Try another USB cable |
| Error starting with `[mc02]` saying the port cannot be opened | Another process holds the board (a bridge, a deployment, an IMU reader). Stop it |
| The SDK refuses `/dev/mc02` and lists several boards | Two boards are plugged in. Set `mc02.port` to the `/dev/serial/by-id/...` path (section 5) |
| No PONG on the first self-test right after plugging in; STATUS then shows `cobs_err=1` | On Linux, ModemManager probes a new serial port with AT commands and holds it for some tens of seconds. Wait half a minute and run the test again. A udev rule that sets `ID_MM_DEVICE_IGNORE` for the board prevents the probing |
| No PONG at all | The firmware is not running, the port is wrong, or the USB cable carries power only and no data |
| LED steady red; self-test reports a CAN clock mismatch (`boot_flags` bit 0) | The CAN bit rate is wrong. Do not connect motors. Re-flash the board (section 8) |
| LED steady red; self-test reports that the IMU failed to initialise (`boot_flags` bit 1) | Unplug the board, plug it in again and repeat the test |
| A whole bus is silent, LEC = 3 | ACK error: the board sent frames and no node acknowledged them. The motors have no power, CAN L and H are exchanged (section 3, rule 6), the termination is missing, or nothing is connected |
| A whole bus is silent, other LEC | See the LEC table below |
| Some ids are missing on a bus | Those motors are not powered, their harness is open, or their CAN id is not the one in the config. Check with `python tools/set_motor_id.py --config <robot yaml> --check` |
| One bus answers with the other bus's ids | The CAN1 and CAN2 harnesses are exchanged. Swap the connectors; do not edit the config |
| Bursts of CRC or COBS errors on the USB link (`crc_err`, `cobs_err` growing) | Poor USB cable or unstable USB power. Watch the USB counters in `[2] STATUS` |
| Bursts of CAN error frames, or `BUS-OFF`, when the motors draw high current | Grounding. Run the separate ground wire from the board to the motor power ground. Use shielded twisted pair for CAN, with the shield grounded at one end |
| During a run the program logs that the board watchdog fired, or that its own loop stalled for longer than the watchdog timeout, and re-homes | The host stalled for more than 100 ms. The joints go to damping and then move back slowly. This is the protection working, not a fault of the board; look at the load and scheduling on the robot computer |
| The program reports a lost link (a line starting with `[mc02]`) and stops driving the motors | The USB connection dropped. Plug the cable back in and start the program again |

LEC values printed by the self-test:

| LEC | Meaning | Typical cause |
|---|---|---|
| 0 | No error | |
| 1 | Stuff error | Wrong bit rate, or noise on the line |
| 2 | Form error | |
| 3 | ACK error | The frame was sent and no node acknowledged it: motors not powered, L and H exchanged, no termination |
| 4 | Bit-1 error | The board sent recessive and read dominant: the bus is held dominant, or L and H are shorted |
| 5 | Bit-0 error | The board sent dominant and did not read it back: transceiver, broken wire, or no common ground |
| 6 | CRC error | |
| 7 | No change | No error since the last read |
